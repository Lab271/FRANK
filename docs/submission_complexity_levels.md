# FRANK Submission Complexity Levels

The FRANK platform supports 6 progressive submission complexity levels, each adding one new dimension of data or structure. These levels are designed for users to incrementally add more detail and context to their submissions as needed. Use this list as a quick reference for the types of submissions and their impact on the database and data model.

**Complexity Levels Overview:**
1. **Absolute Minimal – Bare Essentials Submission**: Only the required fields for an observable sighting; all other fields are auto-generated. Optionally, submitter details and confidence can be provided.
2. **Hit Target Region/Sector WITHOUT organisation_id**: Adds anonymized hit_target metadata (sector/region) without explicit organization linkage.
3. **Hit Target WITH organisation_id (Linkable Observations)**: Adds a separate organization record for the victim and enables richer sector/region analysis.
4. **Enhanced Sighting Metadata**: Adds temporal context, severity, and multiple observable types (network + file).
5. **SIGMA Rule Detection**: Integrates detection rule metadata and effectiveness metrics.
6. **Campaign Attribution and Threat Context**: Adds campaign tracking, MITRE ATT&CK mapping, and impact assessment.



## Purpose

This document defines 6 progressive complexity levels for FRANK threat intelligence submissions, designed to guide users in building submissions of increasing richness and context. The levels validate auto-ID generation, data model flexibility, and the "be forgiving on input, strong on return" principle.

Each level builds incrementally on the previous, adding one new dimension of complexity at a time while maintaining valid, submittable messages throughout. The impact on the database and query capabilities increases with each level.

## Design Philosophy

**Structured Evolution**: These levels follow FRANK's evolutionary design approach by separating concerns and introducing complexity gradually.

**ID Generation Validation**: Primary purpose is to validate that all auto-generated IDs work correctly:
- `submission--{uuid}` - Submission identifiers
- `identity--{uuid}` - Organization identifiers (submitter, hit_target)
- `sighting--{uuid}` - Sighting identifiers
- `{type}--{uuid}` - Observable identifiers (STIX-compliant)
- `sigma--{uuid}` - SIGMA rule identifiers
- `campaign--{uuid}` - Campaign identifiers



## The 6 Complexity Levels




### Level 1: Absolute Minimal - Bare Essentials Submission

**Purpose**: FRANK accepts a submission containing only the bare essentials for an observable sighting, with all other fields (IDs, timestamps) auto-generated by the platform. Optionally, submitter details (such as access_level, organisation_type) and confidence can be provided for richer context.

**Validates**:
- That a submission with only the required fields for an observable sighting is accepted
- Optionally, that additional submitter details and confidence are accepted and preserved
- `submission_id` auto-generation
- `sighting.sighting_id` auto-generation
- `sighting.timestamp` auto-generation (current UTC)
- `observable.id` auto-generation (STIX format: `ipv4--{uuid}`)

**Required Fields**:
- `submitter.organisation_id` - The message must identify the submitting organization (separate from AuthN/Z)

**Optional Fields**:
- `submitter.access_level`, `submitter.organisation_type`, and other submitter metadata
- `sighting.confidence` and multiple observables

**Example (bare minimum)**:
```json
{
  "submission": {
    "submitter": {
      "organisation_id": "identity--f431f809-377b-45e0-aa1c-6a4751cae5ff"
    },
    "sighting": {
      "observables": {
        "network": [
          {
            "type": "ipv4",
            "value": "185.220.102.45"
          }
        ]
      }
    }
  }
}
```

**Example (with submitter options and confidence)**:
```json
{
  "submission": {
    "submitter": {
      "organisation_id": "identity--f431f809-377b-45e0-aa1c-6a4751cae5ff",
      "access_level": "partner",
      "organisation_type": "cyber_partner"
    },
    "sighting": {
      "confidence": 75,
      "observables": {
        "network": [
          {
            "type": "ipv4",
            "value": "185.220.102.45"
          },
          {
            "type": "domain",
            "value": "malicious.example.com"
          }
        ]
      }
    }
  }
}
```

**Expected Auto-Generated Fields**:
```json
{
  "submission": {
    "submission_id": "submission--a1b2c3d4-e5f6-7890-abcd-ef1234567890",
    "timestamp": "2025-01-20T16:45:32.123456Z",
    "format_version": "0.10.1",
    "submission_method": "api",
    "tlp_level": "GREEN"
    "submitter": {
      "organisation_id": "identity--f1a2b3c4-d5e6-7890-abcd-ef1234567890",
      "access_level": "partner",
      "organisation_type": "cyber_partner"
    },
    "sighting": {
      "sighting_id": "sighting--c4d5e6f7-8901-2345-6789-0abcdef12345",
      "timestamp": "2025-01-20T16:45:32.123456Z",
      "confidence": 75,
      "observation_count": 2,
      "observables": {
        "network": [
          {
            "id": "ipv4--9876fedc-ba09-8765-4321-0fedcba98765",
            "type": "ipv4",
            "value": "185.220.102.45"
          },
          {
            "id": "domain--1234abcd-5678-ef90-1234-56789abcdef0",
            "type": "domain",
            "value": "malicious.example.com"
          }
        ]
      }
    }
  }
}
```

**Important Design Notes**:
- **`submitter.organisation_id` is REQUIRED** - The message must explicitly identify the submitting organization
- **Only the bare essentials for a sighting are required** - All other fields (IDs, timestamps, etc.) are auto-generated by the platform
- **Submitter options and confidence can be provided** - If present, these are preserved and included in the database
- **Separation of concerns**: Authorization (AuthN/Z via JWT) is separate from message content (submitter identity)
- The authenticated user's access_level (from JWT) is checked for submission permission, while the message's `submitter.organisation_id` identifies the organization on whose behalf the submission is made

**Database Impact**:
- 1 submission item: `PK: SUB#{submission_id}, SK: SUB`
- 1 organization item: `PK: ORG#{organisation_id}, SK: ORG` (submitter)
- 1 sighting item: `PK: SIGHT#{sighting_id}, SK: SUB#{submission_id}`
- 1 observable index: `PK: OBS#{hash}, SK: SUB#{submission_id}`
- 1 stats item: `PK: OBS#{hash}, SK: STATS`
- 1 audit log: `PK: ACTION#SUBMIT#TS#{timestamp}, SK: TS#{timestamp}#ID#{submission_id}`

### Level 2: Hit Target Region/Sector WITHOUT organisation_id

**Purpose**: Add anonymized hit_target metadata without explicit organization linkage.

**New Complexity**:
- `hit_target` section with sector/region
- **No `organisation_id`** for hit_target (tests sparse GSI2 pattern)
- Tests that observables are stored WITHOUT GSI2PK/SK

**Example**:
```json
{
  "submission": {
    "submitter": {
      "organisation_id": "identity--f431f809-377b-45e0-aa1c-6a4751cae5ff",
      "access_level": "partner"
    },
    "hit_target": {
      "region": "EU",
      "sector": "financial"
    },
    "sighting": {
      "confidence": 75,
      "observables": {
        "network": [
          {
            "type": "ipv4",
            "value": "185.220.102.45"
          }
        ]
      }
    }
  }
}
```

**Validates**:
- Hit target is stored in submission message but NOT as separate organization
- Observable indexing works WITHOUT GSI2PK/SK (sparse index)
- Code handles missing `hit_target.organisation_id` gracefully

**Database Impact**:
- Same as Level 2, but:
  - **No** hit_target organization item created
  - Observable index items have **no** GSI2PK/SK fields
  - Hit target metadata stored only in submission item's `msg` field

**Code Requirement**:
Must check `if hit_target and getattr(hit_target, 'organisation_id', None):` before creating organization item (see [frank_stage3.py:206-222](../../stages/stage3/frank_stage3.py#L206-L222)).

### Level 3: Hit Target WITH organisation_id (Linkable Observations)

**Purpose**: Enable observable linkage to specific victim organizations for sector/region analysis.

**New Complexity**:
- Explicit `hit_target.organisation_id`
- Enables GSI2 indexing for sector/region queries
- Creates separate organization record for victim

**Example**:
```json
{
  "submission": {
    "submitter": {
      "organisation_id": "identity--f431f809-377b-45e0-aa1c-6a4751cae5ff",
      "access_level": "partner"
    },
    "hit_target": {
      "organisation_id": "identity--fd6cbd0fa-b22b-401a-93d7-632023c8f72b",
      "region": "EU",
      "sector": "financial",
      "organisation_size": "large"
    },
    "sighting": {
      "confidence": 87,
      "observables": {
        "network": [
          {
            "type": "ipv4",
            "value": "185.220.102.45"
          },
          {
            "type": "domain",
            "value": "secure-bank-verify.nl"
          }
        ]
      }
    }
  }
}
```

**Validates**:
- Hit target organization record creation
- GSI2PK/SK population for sector analysis
- Observable linkage to victim organization
- Submitter ≠ hit_target validation

**Database Impact**:
- **NEW**: Hit target organization item: `PK: ORG#{hit_target_id}, SK: ORG, GSI1PK: OT#TARGET`
- Observable index items now include:
  - `GSI2PK: SECTOR#{sector}` (e.g., `SECTOR#financial`)
  - `GSI2SK: REGION#{region}#ORG#{org_id}#TS#{timestamp}`
  - `hit_target_org_id` and `hit_target_region` fields

**Query Capabilities Enabled**:
- Find all observables targeting financial sector: `GSI2PK = SECTOR#financial`
- Find all EU financial sector attacks: `GSI2PK = SECTOR#financial AND GSI2SK BEGINS_WITH REGION#EU`
- Find attacks on specific organization: `GSI2SK CONTAINS ORG#{org_id}`

### Level 4: Enhanced Sighting Metadata

**Purpose**: Add temporal context and severity assessment to sightings.

**New Complexity**:
- `first_observed` and `last_observed` timestamps
- `severity` level (low/medium/high/critical)
- `observation_count` tracking
- Multiple observable types (network + file)

**Example**:
```json
{
  "submission": {
    "submitter": {
      "organisation_id": "identity--f431f809-377b-45e0-aa1c-6a4751cae5ff",
      "access_level": "partner"
    },
    "hit_target": {
      "organisation_id": "identity--fd6cbd0fa-b22b-401a-93d7-632023c8f72b",
      "region": "EU",
      "sector": "financial"
    },
    "sighting": {
      "confidence": 87,
      "severity": "high",
      "first_observed": "2025-01-15T10:00:00Z",
      "last_observed": "2025-01-20T14:30:22Z",
      "observation_count": 12,
      "observables": {
        "network": [
          {
            "type": "ipv4",
            "value": "185.220.102.45",
            "role": "c2_server",
            "port": 443,
            "protocol": "https"
          }
        ],
        "file": [
          {
            "type": "file_hash_sha256",
            "value": "a1b2c3d4e5f67890abcdef1234567890abcdef1234567890abcdef1234567890"
          }
        ]
      }
    }
  }
}
```

**Validates**:
- Datetime validation and serialization
- `first_observed < last_observed` validation
- Severity enum validation
- Multiple observable category handling

**Database Impact**:
- Sighting item includes enhanced metadata
- Observable index now tracks file observables
- Stats items for both network and file types

### Level 5: SIGMA Rule Detection

**Purpose**: Integrate community-validated detection rules and effectiveness metrics.

**New Complexity**:
- `sigma_detection` section with rule metadata
- Auto-generation of `sigma--{uuid}` rule IDs
- Rule effectiveness and false positive tracking

**Example**:
```json
{
  "submission": {
    "submitter": {
      "organisation_id": "identity--f431f809-377b-45e0-aa1c-6a4751cae5ff",
      "access_level": "partner"
    },
    "hit_target": {
      "organisation_id": "identity--fd6cbd0fa-b22b-401a-93d7-632023c8f72b",
      "region": "EU",
      "sector": "financial"
    },
    "sighting": {
      "confidence": 87,
      "severity": "high",
      "sigma_detection": {
        "rule_name": "Suspicious PowerShell Execution with Base64",
        "rule_version": "1.2",
        "rule_status": "stable",
        "rule_effectiveness": 0.85,
        "false_positive_rate": 0.02,
        "sigma_yaml": "title: Suspicious PowerShell Execution\nid: abc123\nstatus: stable\ndetection:\n  selection:\n    EventID: 4688\n    CommandLine|contains: '-enc'\n  condition: selection"
      },
      "observables": {
        "network": [
          {
            "type": "ipv4",
            "value": "185.220.102.45"
          }
        ]
      }
    }
  }
}
```

**Validates**:
- SIGMA rule ID auto-generation
- Rule effectiveness scoring
- Detection metadata preservation

**Database Impact**:
- Sighting item includes full SIGMA detection data
- Enables future querying by rule_name or rule_status

## Complexity Progression Summary

| Level | Focus | Anonymous IDs | Key Validation |
|-------|-------|-------------------|----------------|
| 1 | Absolute minimal | ALL generated (submission, submitter, sighting, observable) | Auto-ID generation works, submitter/confidence options |
| 2 | Anonymous victim | Explicitely NO HitTarget and no generation | Sparse GSI2 (no hit_target org) |
| 3 | Linked victim | HitTarget provided | GSI2 population, org linkage |
| 4 | Enhanced Sighting Metadata | None, all provided | Datetime validation, severity |
| 5 | SIGMA detection | + sigma rule ID provided| Detection metadata |
| 6 | Campaign attribution | + campaign ID provided | Strategic intelligence |


## Database Query Patterns by Level

### Level 1-2 Queries
```python
# Get submission by ID
table.get_item(Key={'PK': f'SUB#{submission_id}', 'SK': 'SUB'})

# Get submitter's submissions
table.query(IndexName='GSI1', KeyConditionExpression='GSI1PK = :pk',
            ExpressionAttributeValues={':pk': f'SUBMITTER#{org_id}'})
```

### Level 4+ Queries (GSI2 Enabled)
```python
# Find observables targeting financial sector
table.query(IndexName='GSI2', KeyConditionExpression='GSI2PK = :pk',
            ExpressionAttributeValues={':pk': 'SECTOR#financial'})

# Find EU financial sector attacks
table.query(IndexName='GSI2',
            KeyConditionExpression='GSI2PK = :pk AND begins_with(GSI2SK, :sk)',
            ExpressionAttributeValues={
                ':pk': 'SECTOR#financial',
                ':sk': 'REGION#EU'
            })
```

## Alignment with FRANK Design Principles

### Evolutionary Design
- **One complexity at a time**: Each level adds exactly one new concept
- **Working at every stage**: All 6 levels are valid, submittable messages
- **Fallback capability**: Can always fall back to Level 1 minimal submission

### "Be Forgiving on Input, Strong on Return"
- **Input**: All levels accept minimal data, auto-generate missing IDs, besides the HitTarget
- **Return**: All levels return complete, normalized, validated data with IDs
